# L15 — Disaster Recovery

## Summary
Disaster recovery (DR) is about maintaining business continuity when systems fail. The exam tests four metrics (RPO, RTO, MTBF, MTTR), three site types (hot/warm/cold), two HA approaches (active-active vs active-passive), and two testing methods (tabletop vs validation). Almost all of this is terminology — there's no CLI config to learn.

---

## Core Concepts

### DR Metrics

| Metric | Full Name | What It Measures | Goal |
|--------|-----------|-----------------|------|
| **RPO** | Recovery Point Objective | Max acceptable data loss (how old can the restore point be?) | Minimize — smaller = more frequent backups |
| **RTO** | Recovery Time Objective | Max time systems can be down before business impact | Minimize — smaller = faster recovery |
| **MTBF** | Mean Time Between Failures | Average uptime between failures (reliability) | Maximize — longer = more reliable |
| **MTTR** | Mean Time To Repair | Average time to restore after a failure | Minimize — shorter = faster repair |

**Key distinction:** RPO is about **data** (what you lose); RTO is about **time** (how long you're down). These are the two most-tested traps on the exam.

**Example:** "The last backup ran 12 hours ago — the RPO is 12 hours." If the system crashes now, you lose up to 12 hours of data. That's the recovery point, not the recovery time.

**MTBF vs MTTR:** Think of a reliability timeline:
```
[up]——[MTBF]——[fail]——[MTTR]——[up]——[MTBF]——...
```
MTBF = the long up-time stretch; MTTR = the short repair window. You want MTBF long and MTTR short.

### DR Site Types

| Site | Equipment | Data | Changeover Time | Cost |
|------|-----------|------|----------------|------|
| **Hot** | Full stack, live mirror | Current (replicated in real time) | Minutes | Highest |
| **Warm** | Hardware in place | Recent backup (not real-time) | Hours | Medium |
| **Cold** | Empty space (rented) | None — must be loaded | Days | Lowest |

**Hot site:** Everything is running and synchronized. Flip the switch. Highest carrying cost — you're paying for a full duplicate that sits idle. In modern environments, this is typically a cloud region running in active standby.

**Warm site:** Hardware exists at the site but data isn't live. You'd ship/restore the latest backup tapes (or pull from cloud storage). Good middle ground — some lead time, lower cost.

**Cold site:** Just a facility — rented floor space or cloud account. No equipment, no data. Must be fully provisioned before cutover. Lowest cost, slowest recovery.

**In cloud terms:** Hot = a second region actively running your workload. Warm = AMIs/snapshots ready, not running. Cold = an empty VPC with nothing deployed.

### High Availability: Active-Active vs Active-Passive

**Active-Active:**
- All nodes process traffic simultaneously
- Load is distributed across all devices
- If one fails, remaining nodes absorb the workload
- Example: four servers behind a load balancer — all four handle requests at all times
- Requires enough headroom so surviving nodes can absorb the failed node's load

**Active-Passive:**
- One or more standby nodes sit idle until the active node fails
- Passive node doesn't process traffic until failover is triggered
- Example: backup power supply, secondary control plane on a multi-layer switch, HSRP standby router
- Higher cost because passive hardware is idle; immediate failover once triggered
- Question: does it **fail back** automatically after the primary recovers? Design decision.

**Trick:** HSRP (L09) is an active-passive FHRP — one active gateway, one standby. The standby doesn't forward traffic until the active fails.

**VLAN optimization pattern:** Use one device active on VLAN 10, the other active on VLAN 20, with each being passive for the other's VLAN. This gives you load distribution while maintaining redundancy — sometimes called *per-VLAN load sharing*.

### DR Testing

**Tabletop Exercise:**
- Paper/discussion walkthrough — no systems are actually moved
- Goal: verify everyone knows their role, the playbook is current, communication paths are clear
- Identifies gaps in documentation and stakeholder responsibility before a real event
- Low risk, low cost; should be done periodically

**Validation Test:**
- Real-world test of actual recovery capability
- Could be: full failover to the hot/warm site, restoring from backup, or spinning up the cold site
- Tests actual RTO — how long does it really take vs. how long you think it takes?
- Could be non-disruptive (bring up the DR site without cutting over live traffic) or a full cutover drill
- Validates backup integrity — restoring a backup you've never tested is not a DR plan

**Exam trap:** Tabletop = discussion/planning. Validation = real test. If a question describes "walking through a scenario with stakeholders," that's tabletop. If it describes "actually failing over to the backup site," that's a validation test.

## Key Terms

| Term | Definition |
|------|-----------|
| RPO | Max acceptable data loss expressed as time since last backup |
| RTO | Max acceptable downtime before business impact |
| MTBF | Average uptime between failures — measures reliability |
| MTTR | Average repair time after failure — measures responsiveness |
| Hot site | Fully equipped, live-data DR site; fastest recovery, highest cost |
| Warm site | Equipped but not live-data; medium recovery time and cost |
| Cold site | Empty facility; slowest recovery, lowest cost |
| Active-Active | All nodes process live traffic; failure redistributes load |
| Active-Passive | One node standby; takes over only on failure |
| Fail back | Returning workload to primary after it recovers from failure |
| Tabletop exercise | Discussion-based DR walkthrough; no real systems moved |
| Validation test | Real-world test of DR processes; may include full failover |
| Business Impact Analysis (BIA) | Assessment of how failures affect business operations |
| Business Continuity | Broader strategy for keeping operations running during disruption |

## Real-World Connections

**k3s lab:** Your k3s cluster is active-active at the pod level — if a pod crashes, the others absorb traffic while the scheduler restarts it. At the node level, you likely have a single control plane (active-passive model with etcd as the state store).

**AWS:** Multi-AZ deployments implement active-active (RDS read replicas spread across AZs) or active-passive (RDS Multi-AZ failover). S3 cross-region replication sets your RPO. RTO depends on how fast your failover automation triggers.

**GCP:** Cloud SQL high availability uses active-passive — primary in one zone, standby in another. Failover happens automatically but the standby isn't serving queries until the primary fails.

**Enterprise backup example:** Daily backup at midnight → RPO = up to 23h59m. If you need RPO of 1 hour, you need near-continuous replication (WAL shipping, CDC, or synchronous replication).

## Troubleshooting Scenario

**Scenario:** Your organization has a warm DR site. A datacenter fire occurs at 2:00 AM. By 6:00 AM the DR site is operational. IT reports they restored from last night's backup (taken at 11:00 PM).

**Analysis:**
- **RTO:** 4 hours (2:00 AM failure → 6:00 AM recovery). Is that within your agreed RTO?
- **RPO:** ~3 hours of data lost (11:00 PM backup → 2:00 AM failure). Is that within your agreed RPO?
- **Site type:** Warm — hardware was already there, but had to restore backup data. Cold would have taken longer; hot would have been near-instant.
- **Next steps:** Run a validation test to confirm the actual RTO matches the documented RTO. Update backup frequency if 3h data loss isn't acceptable.

## Hands-On Ideas

1. **Calculate your k3s RPO:** How often does your persistent storage get snapshotted? That interval is your RPO.
2. **Simulate a pod failure:** Kill a deployment pod and measure how long before traffic restores — that's your MTTR at the pod level.
3. **Tabletop your lab:** Write a one-page runbook for "what if the k3s control plane node dies?" Walk through it without actually doing it.
4. **Cloud DR design:** Sketch a warm-site architecture in AWS — what services would you pre-provision, and what would you restore from snapshot?

## Quiz

1. Your last backup completed at 3:00 AM. A disk failure occurs at 8:00 AM. Systems are restored by 11:00 AM. What is the RPO?
   - A) 8 hours  B) 3 hours  C) 5 hours  D) 11 hours

2. Which DR metric describes how long your systems can remain offline before unacceptable business impact?
   - A) RPO  B) MTBF  C) RTO  D) MTTR

3. A company has a DR site with all equipment installed and synchronized data. What type of site is this?
   - A) Cold  B) Warm  C) Hot  D) Passive

4. Your load balancer has four web servers all processing live requests. One server crashes. Traffic shifts to the remaining three. What HA model is this?
   - A) Active-Passive  B) Active-Active  C) Hot standby  D) Cold standby

5. A network team gathers in a conference room and walks through what they would do if the primary datacenter lost power. No systems are actually moved. This is a:
   - A) Validation test  B) Tabletop exercise  C) Failover drill  D) Recovery point test

6. Which metric measures the average uptime between system failures and should be maximized?
   - A) MTTR  B) RTO  C) RPO  D) MTBF

**Answers:** 1-C (5h data loss, 3AM→8AM), 2-C, 3-C, 4-B, 5-B, 6-D
