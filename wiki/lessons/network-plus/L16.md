# L16 — IP Services

## Summary
IP Services covers the foundational protocols that make modern networks usable: DHCP (v4 and IPv6 SLAAC), DNS with all its record types and security extensions, and time protocols (NTP/PTP/NTS). This lesson is exam-dense — expect questions on DHCP DORA, relay agents, specific DNS record functions, PTR record format, DNSSEC vs DoH/DoT, and NTP vs PTP ports.

---

## Core Concepts

### DHCP — Dynamic Host Configuration Protocol

**What DHCP hands out:**
- IP address
- Subnet mask
- Default gateway (default router)
- DNS server (DNS resolver address)
- Optional: domain name suffix, TFTP server for config download, etc.

**Scope configuration elements:**
| Element | Purpose |
|---------|---------|
| **Scope** | The pool definition — network range, subnet mask, lease duration |
| **Lease** | How long an IP assignment is valid before renewal required |
| **Reservation** | Ties a specific IP to a MAC address — device always gets the same IP |
| **Exclusion** | Removes an IP from the pool (for statically assigned devices) |

**Reservation vs Exclusion distinction:**
- Reservation = DHCP *does* hand out the address, but always to the same MAC (servers, printers)
- Exclusion = DHCP *never* hands out the address — it's used for manual static config

**DHCP DORA — 4-step process:**
```
Client → Discover  (broadcast — finding a server)
Server → Offer     (broadcast — "I can give you this IP")
Client → Request   (broadcast — "I'll take that offer")
Server → Acknowledge (unicast — confirmed, here are your settings)
```
Critical detail: **Discover is a broadcast** — routers don't forward broadcasts. This creates the relay agent requirement.

**DHCP Relay / Helper:**
When the client and DHCP server are on different subnets:
1. Client broadcasts Discover on local subnet
2. Router intercepts and **unicasts** it to the DHCP server IP (configured as `ip helper-address` on Cisco)
3. Server sends Offer back through the relay
4. Client completes DORA normally

The router becomes the **DHCP relay agent** (also called IP helper). This is why a single DHCP server can serve multiple subnets — without relay, you'd need a DHCP server on every subnet.

**Security implication:** You can detect rogue DHCP servers by monitoring where Offer and Acknowledge packets originate. Only known DHCP server IPs should be sending those.

### IPv6 — SLAAC (Stateless Address Autoconfiguration)

IPv6 devices can self-configure without a DHCP server using SLAAC:

**Process:**
1. Interface generates a **link-local address** (prefix `FE80::/10`) using EUI-64 from its MAC address
2. Sends a **Router Solicitation** (multicast) — "Any routers out there?"
3. IPv6 router responds with a **Router Advertisement** — contains network prefix and router IP
4. Device builds its full global unicast address: `[prefix from RA] + [EUI-64 host portion]`
5. Gets DNS server via **stateless DHCPv6** (server doesn't track what it gives out)

**What comes from where:**
| Config element | Source |
|---------------|--------|
| Host address portion | EUI-64 (derived from MAC) |
| Network prefix + prefix length | Router Advertisement |
| Default gateway | Router Advertisement (the router's own address) |
| DNS server | Stateless DHCPv6 |

**Key distinction:** Stateless DHCPv6 gives out DNS info only — not IP addresses. The IP is self-assigned. Stateful DHCPv6 works more like v4 DHCP with a central pool.

### DNS — Domain Name System

**Architecture:**
- **DNS Resolver** — your locally configured DNS server (configured by DHCP or admin). Goes and finds answers on your behalf. Not authoritative for anything.
- **Name Server** — authoritative for a specific domain. Holds the actual records for that organization.
- **Port:** UDP 53 (most queries). TCP 53 for zone transfers or large responses.

**Query flow:**
```
Your device → Resolver (local/ISP/8.8.8.8)
Resolver → Name Server for the target domain
Resolver returns answer → Your device
```

**DNS Record Types (all testable):**

| Record | Full Name | What It Does |
|--------|-----------|-------------|
| **A** | Address | Maps hostname → IPv4 address |
| **AAAA** | IPv6 Address | Maps hostname → IPv6 address (4x "A" = 4x bits) |
| **NS** | Name Server | Identifies the authoritative name server(s) for a zone |
| **MX** | Mail Exchanger | Identifies mail servers for a domain; includes priority number (lower = preferred) |
| **CNAME** | Canonical Name | Alias — points one name to another name (not directly to an IP) |
| **TXT** | Text | Free-form text; used for SPF, DKIM, DMARC email security records |
| **PTR** | Pointer | Reverse lookup — maps IP → hostname; uses `in-addr.arpa` domain |

**CNAME chain:** `alias.example.com → CNAME → real.example.com → A → 1.2.3.4`. The alias doesn't have its own A record; it points to the canonical name.

**PTR record format:** `in-addr.arpa`
- For IP `192.168.1.100`, the PTR record is: `100.1.168.192.in-addr.arpa`
- Written in reverse-octet order + `.in-addr.arpa`
- Used in security forensics — you have an IP from packet analysis, you want to know the domain

**Response types:**
- **Authoritative** — from the actual name server for that domain (the source of truth)
- **Non-authoritative** — from a resolver's cache (may be stale)
- **Recursive** — resolver does the full lookup chain on your behalf and returns the final answer

**TTL:** Time-to-live on a DNS record. Controls how long resolvers cache the answer. If an org changes IPs, old TTL can cause stale cache issues.

**CLI tools:**
```bash
dig google.com            # full DNS response with all sections
dig google.com +short     # just the IP
dig google.com MX         # query specific record type
dig @8.8.8.8 google.com  # query a specific resolver/nameserver
nslookup google.com       # Windows-friendly alternative
```

### DNS Security

DNS was designed without security — queries and responses are plaintext and easily spoofed.

**DNSSEC (DNS Security Extensions):**
- Adds a **digital signature** to DNS records (using public key cryptography)
- Resolver can verify the record is authentic and hasn't been tampered with
- Protects **integrity** of the DNS response — is this really from google.com's name server?
- Does NOT encrypt queries (someone on the wire can still see what you're looking up)

**DoH — DNS over HTTPS:**
- Tunnels DNS queries inside HTTPS (port **443**)
- Leverages TLS encryption of HTTPS
- Encrypts both the query and the response
- Browsers increasingly use this by default (Firefox, Chrome)
- Problem for enterprise: DNS-based filtering/security can't inspect encrypted DNS traffic

**DoT — DNS over TLS:**
- Direct TLS encryption of DNS protocol (port **853**)
- Same goal as DoH but uses a dedicated port
- Easier for network devices to identify (vs DoH blending into HTTPS traffic)

**Exam trap — DNSSEC vs DoH/DoT:**
- DNSSEC = signature verification (authenticity/integrity, not confidentiality)
- DoH/DoT = encryption of DNS traffic (confidentiality of queries and responses)
- They solve different problems and are complementary

### /etc/hosts File

Pre-DNS method for name resolution. Still present on every OS.

- **Linux:** `/etc/hosts`
- **Windows:** `C:\Windows\System32\drivers\etc\hosts`
- **Checked before DNS query** — if an entry exists here, no DNS lookup happens
- Format: `<IP address>    <hostname>    [aliases...]`
- Loopback entry always present: `127.0.0.1   localhost   localhost.localdomain`
- Static — changes must be made manually per device; doesn't scale

**Use cases today:** Overriding DNS for testing, blocking domains (map to 127.0.0.1), container/k3s hostnames for local dev.

### Time Protocols

**Why time matters:** Logging, certificate validity, Kerberos authentication, financial transactions, and forensic timeline reconstruction all depend on synchronized clocks. A 5-minute clock skew breaks Kerberos by default.

**NTP — Network Time Protocol:**
- UDP port **123**
- Client sends request → time server returns current timestamp
- Stratum model: Stratum 0 = atomic clock; Stratum 1 = directly connected to Stratum 0; and so on
- Can use **pre-shared key** for authentication — server won't respond to unauthenticated requests
- Accuracy: millisecond range

**PTP — Precision Time Protocol (IEEE 1588):**
- UDP ports **319** (event messages) and **320** (general messages)
- Multicast address: `224.0.1.129`
- Designed for sub-microsecond accuracy
- Used in financial trading, 5G/cellular base stations, industrial control systems
- Updated in 2018 (PTPv2)

**NTS — Network Time Security:**
- NTP with TLS encryption
- Solves NTP's original lack of security
- Same purpose as NTP (time sync) but uses TLS to secure the exchange

**Port cheat sheet:**
| Protocol | Port | Transport |
|----------|------|-----------|
| NTP | 123 | UDP |
| PTP (event) | 319 | UDP (multicast) |
| PTP (general) | 320 | UDP (multicast) |
| DNS | 53 | UDP (TCP for large/zone transfer) |
| DoT | 853 | TCP (TLS) |
| DoH | 443 | TCP (HTTPS/TLS) |

## Key Terms

| Term | Definition |
|------|-----------|
| DORA | Discover → Offer → Request → Acknowledge — DHCP 4-step process |
| DHCP Scope | The defined pool of IPs, lease time, and options a DHCP server hands out |
| DHCP Reservation | IP bound to a specific MAC — device always gets the same address |
| DHCP Exclusion | IP range within scope withheld from dynamic assignment |
| DHCP Relay / IP Helper | Router that forwards DHCP broadcasts across subnet boundaries |
| SLAAC | Stateless Address Autoconfiguration — IPv6 self-addressing from RA prefix + EUI-64 |
| Router Advertisement | IPv6 router broadcast containing network prefix and gateway — enables SLAAC |
| EUI-64 | Host ID portion of IPv6 address derived from 48-bit MAC address |
| DNS Resolver | Your local DNS server — queries on your behalf; caches results |
| DNS Name Server | Authoritative server for a domain — holds actual records |
| A record | Hostname → IPv4 |
| AAAA record | Hostname → IPv6 |
| MX record | Mail exchanger for a domain; includes priority |
| CNAME | Alias pointing to another name (not directly to IP) |
| TXT record | Text info; used for SPF/DKIM/DMARC |
| PTR record | Reverse lookup — IP → hostname; format uses `in-addr.arpa` |
| NS record | Authoritative name server for a zone |
| DNSSEC | Adds digital signatures to DNS records to verify authenticity |
| DoH | DNS over HTTPS — encrypts DNS queries via port 443 |
| DoT | DNS over TLS — encrypts DNS queries via port 853 |
| NTP | Network Time Protocol — UDP 123; millisecond clock sync |
| PTP | Precision Time Protocol — UDP 319/320; sub-microsecond for high-precision use |
| NTS | Network Time Security — NTP with TLS for secure time sync |
| TTL | Time-to-live on a DNS record; controls cache duration |

## Real-World Connections

**k3s lab:** Your pods get IPs from kube-proxy's IPAM — not DHCP, but analogous scope/reservation logic (ClusterIP ranges). CoreDNS in k3s is the in-cluster DNS resolver — it handles `.svc.cluster.local` resolution the same way a corporate resolver handles internal domains. Your `/etc/hosts` on each node is checked before CoreDNS.

**DHCP relay in your network:** Every home router is running DHCP for your LAN. Your ISP's gateway is a DHCP relay passing your router's WAN request to the ISP's DHCP server.

**SLAAC in production:** IPv6-enabled GCP/AWS VPCs use SLAAC for host auto-configuration. The cloud router sends RAs; instances derive their IPv6 addresses automatically. See GCP02 (IPv6 in Google Cloud).

**DoH in enterprise:** A major headache for enterprise security teams — if users' browsers use DoH to 8.8.8.8, the corporate DNS filtering proxy is bypassed. Mitigation: block port 443 to known DoH providers or run a trusted DoH server internally.

**PTP in telecom:** Your 5G NR sidelink work (V2X) depends on PTP for radio frame synchronization. 5G base stations (gNBs) use PTP to synchronize their timing — without it, inter-cell handoffs break.

## Troubleshooting Scenario

**Scenario:** A new VLAN (192.168.50.0/24) was configured on a switch. Hosts on this VLAN can't get IP addresses. Hosts on other VLANs get DHCP fine. The DHCP server is on VLAN 10 (10.0.10.5).

**Diagnosis path:**
1. DHCP Discover is a broadcast — it won't cross the VLAN boundary to VLAN 10
2. Check the inter-VLAN router/L3 switch: is `ip helper-address 10.0.10.5` configured on the VLAN 50 SVI?
3. If not, add it — that's the relay agent telling the router to forward DHCP broadcasts to the server
4. If the helper is there, check: does the DHCP scope include the 192.168.50.0/24 range? If the scope doesn't exist, no offers will come back

**Root cause:** Missing DHCP relay (ip helper-address) on the new VLAN's SVI. Classic operational error when adding VLANs.

## Hands-On Ideas

1. **dig reconnaissance:** Run `dig google.com`, `dig google.com MX`, `dig google.com NS`, `dig -x 8.8.8.8` (PTR lookup) and map each output to the record types from this lesson.
2. **k3s CoreDNS:** Run `kubectl exec -it <any-pod> -- nslookup kubernetes.default.svc.cluster.local` — this hits CoreDNS, which acts as your cluster's authoritative name server.
3. **DHCP relay simulation:** Identify which VLANs in your environment have DHCP relay configured vs static addressing. Trace a DORA exchange with Wireshark/Kubeshark.
4. **SLAAC observation:** On a Linux box, run `ip -6 addr` and identify the `FE80::` link-local address — that's the SLAAC-generated address before a router advertisement arrives.
5. **hosts file test:** Add a fake entry to `/etc/hosts` (`127.0.0.1 testdomain.local`) and `ping testdomain.local` — it resolves without DNS.

   - A) CNAME  B) MX  C) PTR  D) TXT

   - A) A  B) NS  C) CNAME  D) MX

   - A) A DHCP Offer with a full IPv6 config  
   - B) A Router Advertisement containing the network prefix, used to build its global address  
   - C) A DNSSEC response with the gateway's certificate  
   - D) A PTR record mapping its MAC to its link-local address

6. What is the difference between DNSSEC and DoT?
   - A) DNSSEC encrypts the DNS query; DoT verifies the DNS response signature
   - B) DNSSEC signs records to verify authenticity; DoT encrypts the DNS exchange in transit
   - C) DNSSEC uses port 853; DoT uses port 443
   - D) They are the same technology with different names

7. Which time protocol provides sub-microsecond precision and is commonly used in financial trading and 5G base stations?
   - A) NTP (UDP 123)  B) PTP (UDP 319/320)  C) NTS (TLS-secured NTP)  D) SNTP
