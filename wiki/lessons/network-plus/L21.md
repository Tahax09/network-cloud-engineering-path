# L21 — Network Troubleshooting Methodology

## Summary
This is the first objective of Domain 5 (22% of the exam, the largest domain). It covers CompTIA's **7-step troubleshooting methodology**. The exam rarely asks you to *solve* a problem here. Instead it gives a **narrative** ("the technician has done X and Y…") and asks **which step comes next** or **which step is happening now**. Memorize the steps **in order** and the **sub-tasks under each step**, because questions are often written using a sub-task name rather than the step name.

---

## Core Concepts

### The 7 Steps (memorize the order)

```
1. Identify the problem
        │
2. Establish a theory of probable cause
        │
3. Test the theory to determine the cause ──── not confirmed ──▶ new theory (back to 2) or ESCALATE
        │ confirmed
4. Establish a plan of action to resolve the problem and identify potential effects
        │
5. Implement the solution or escalate as necessary
        │
6. Verify full system functionality and, if applicable, implement preventive measures
        │
7. Document findings, actions, outcomes, and lessons learned
```

**Mnemonic:** **I**dentify · **E**stablish theory · **T**est · **P**lan · **I**mplement · **V**erify · **D**ocument →
"**I** **E**at **T**acos **P**retty **I**ntensely **V**ery **D**aily."

---

### Step 1 — Identify the Problem

Sub-tasks (any of these in a question means **step 1**):

| Sub-task | What it means in practice |
|----------|--------------------------|
| **Gather information** | Logs, alerts, monitoring dashboards ([[L14]]), tickets |
| **Question users** | "It's not working" is not a problem statement. Ask what exactly fails, since when, and for whom |
| **Identify symptoms** | "Can reach Google but not the timesheet app" is far more useful than "internet down" |
| **Determine if anything has changed** | Updates, installs, reboots, new location, config changes. Usually the most valuable question. Check change records ([[L13]]) |
| **Duplicate the problem, if possible** | Reproduce it on another machine or account to see if it's user-, location-, or permission-specific |
| **Approach multiple problems individually** | Can't reach internal resources *and* partner resources? Treat them as separate tickets until proven related |

**Scope questions to ask:** Does it affect one user or everyone? One site or all sites? One app or all apps? Is it permission-based? Location-based?

---

### Step 2 — Establish a Theory of Probable Cause

| Sub-task | Detail |
|----------|--------|
| **Question the obvious** | Power, cable seated, link light, Wi-Fi on. Check the simple lower-layer causes before chasing exotic ones |
| **Know expected behavior** | You can't call something abnormal without a baseline. Did this ever work for this user? |
| **Consider multiple approaches** | Top-to-bottom, bottom-to-top, or divide and conquer (below) |

#### The Three OSI Approaches ([[L01]])

| Approach | Start | Path | Best when |
|----------|-------|------|-----------|
| **Top-to-bottom** | L7 application | Application → ports → IP/DNS → ARP → physical | Problem looks application-specific (one app fails, others work) |
| **Bottom-to-top** | L1 physical | Power/cable → link → ARP → IP/DNS → ports → app | Total outage, new install, physical change suspected |
| **Divide and conquer** | Middle (usually L3) | Test in the middle, then go up or down based on the result | Experienced troubleshooter; fastest on average |

**Divide and conquer in action:**
```
ping 10.1.1.50        ✔ works  → L1–L3 fine → move UP:   nslookup server.corp  ✘ → DNS problem
                      ✘ fails  → move DOWN: check IP config, gateway, ARP, link
```
**Classic exam logic:** reachable **by IP but not by name** → **DNS**.

---

### Step 3 — Test the Theory to Determine the Cause

- **Theory confirmed** → determine the next steps to resolve the problem (go to step 4).
- **Theory not confirmed** → **establish a new theory** (back to step 2) **or escalate**.

**Example chain:**
| Theory | Test | Result → next |
|--------|------|---------------|
| IP configuration issue | `ipconfig` / `ip a`: is it a **169.254.x.x (APIPA)** address? | APIPA means no DHCP lease → `ipconfig /renew`, then check DHCP server / relay ([[L16]]) |
| Valid IP, maybe gateway | `ping <default gateway>` | Fails → check gateway config/VLAN; succeeds → new theory |
| DNS | `nslookup` / `dig` | Wrong/no answer → DNS server or record issue |

**Escalation** happens when you lack access or authority (tiered support, access-control limits) or the fix belongs to someone else (vendor, manufacturer, ISP, another team).

---

### Step 4 — Establish a Plan of Action & Identify Potential Effects

Before changing anything:
- What **steps** are needed?
- What is the **rollback plan** if it doesn't work?
- What are the **effects on other systems** (blast radius)?
- Does this require **change management** approval ([[L13]])?

---

### Step 5 — Implement the Solution or Escalate

- **Implement** if it's within your authority.
- **Escalate** if approval or access is needed.
- **No ad hoc changes** on networks with a formal change process, even mid-incident. That's how undocumented drift starts.

---

### Step 6 — Verify Full System Functionality & Implement Preventive Measures

- Confirm with the **user who raised the ticket**. It isn't fixed until they say it works.
- Check **performance** (bandwidth, delay, loss) and **reachability**, and **compare to the baseline**.
- **Preventive measures:** if the problem could recur, add a control or process (monitoring alert, config template, DHCP snooping, a UPS…).

"Full system" matters: the fix must not break anything else.

---

### Step 7 — Document Findings, Actions, Outcomes, and Lessons Learned

- **What** was wrong, **how** it was diagnosed, **what config change** fixed it. This feeds the knowledge base and change records.
- Undocumented fixes come back to bite: a reboot or hardware swap restores the *old* config, and nobody knows what changed.
- **Lessons learned:** **blameless** review of what worked, what didn't, and what would have helped (better information flow, read access to logs, etc.).

**Exam trap:** documentation is the **last** step, but in reality you document *throughout*. If a question asks which step is **last** → document.

## Step-Identification Cheat Sheet

| If the question says… | Step |
|----------------------|------|
| "asks the user what changed", "reproduces the issue", "checks logs", "gathers information" | **1 Identify** |
| "suspects", "considers", "checks the cable first", "uses top-down approach" | **2 Theory** |
| "pings to confirm", "the theory is not confirmed" | **3 Test** |
| "theory confirmed" → *next?* | **4 Plan of action** |
| "theory not confirmed" → *next?* | **Establish new theory (2) or escalate** |
| "considers rollback / impact on other systems" | **4 Plan** |
| "applies the change", "submits to senior engineer" | **5 Implement / escalate** |
| "confirms with the user", "compares to baseline", "adds monitoring so it won't recur" | **6 Verify + preventive** |
| "updates the ticket / knowledge base", "lessons learned" | **7 Document** |

## Key Terms

| Term | Definition |
|------|-----------|
| Troubleshooting methodology | CompTIA's 7-step ordered process for resolving issues |
| Identify the problem | Step 1: gather info, question users, symptoms, changes, duplicate, separate multiple problems |
| Theory of probable cause | Step 2: hypothesis about the root cause; question the obvious |
| Question the obvious | Rule out simple causes (power, cables, link) first |
| Top-to-bottom | OSI troubleshooting starting at the application layer |
| Bottom-to-top | OSI troubleshooting starting at the physical layer |
| Divide and conquer | Start mid-stack (often ping at L3), then move up or down |
| Test the theory | Step 3: confirm or reject the hypothesis |
| Escalation | Handing off to a higher tier, another team, or a vendor when outside your authority or expertise |
| Plan of action | Step 4: steps, rollback, effects on other systems |
| Rollback plan | How to undo the change if it fails |
| Verify full system functionality | Step 6: confirm the fix with the user and baseline, with no collateral damage |
| Preventive measures | Controls added so the issue doesn't recur |
| Lessons learned | Blameless review of what to improve |
| APIPA | 169.254.0.0/16 self-assigned address meaning DHCP failed |

## Real-World Connections

**k3s lab:** A pod can't reach Elasticsearch, run through the steps:
1. **Identify:** Which pods? Since when? *What changed?* (`kubectl get events -A --sort-by=.lastTimestamp`, recent `helm history`, NetworkPolicy edits)
2. **Theory:** Divide and conquer at L3/L4: `kubectl exec -it <pod> -- nc -zv elasticsearch-es-http.elastic 9200`
3. **Test:** By ClusterIP works but by name fails → CoreDNS (`kubectl -n kube-system logs deploy/coredns`). Both fail → NetworkPolicy or Service endpoints (`kubectl get endpoints`)
4. **Plan:** Patch the NetworkPolicy in Git, know the rollback (`git revert` / `kubectl rollout undo`)
5. **Implement:** via GitOps, not `kubectl edit` (no ad hoc changes)
6. **Verify:** Kibana loads, Kubeshark shows clean 200s, latency matches the baseline. **Preventive:** alert on endpoint count = 0
7. **Document:** commit message plus a note in `wiki/labs/k3s-lab.md`

**Production SRE parallel:** This methodology maps onto incident response: triage (1) → hypothesis (2–3) → mitigation plan (4) → change via deploy pipeline (5) → verify SLOs (6) → **blameless postmortem** (7). Google's SRE postmortem culture is the "lessons learned, not blame" principle at scale.

**AWS:** "Can reach by IP not by name" in a VPC → check `enableDnsSupport`/`enableDnsHostnames` and Route 53 Resolver rules. VPC **Reachability Analyzer** is divide-and-conquer as a service: it tells you which hop (SG, NACL, route table) blocks the path.

## Troubleshooting Scenario

**Scenario:** A user reports "the internet is down." The technician asks questions and learns the user can browse external sites but cannot open the internal HR portal. A coworker at the next desk can open it. The user says a VPN client was installed yesterday. The technician suspects the VPN client added a route or DNS setting that overrides internal resolution. `nslookup hr.corp.local` returns a public IP instead of the internal 10.x address, confirming the theory.

**Questions:**
1. Which actions so far belong to **step 1**? → Questioning the user, identifying the symptom (external works, HR fails), duplicating (coworker works → user-specific), **determining what changed** (VPN client install).
2. What step is the `nslookup` check? → **Step 3, test the theory** (and it's confirmed).
3. What comes **next**? → **Step 4, establish a plan of action**: e.g., configure the VPN for split DNS or remove the client, check the effect on other VPN users, and get change approval if it's a fleet-wide client config.
4. After the fix → **verify** HR portal access with the user **and** that the VPN still works (full system), add a preventive measure (fix the VPN client profile for all users), then **document**.

## Hands-On Ideas

1. **Practice divide and conquer on your own network:**
   ```bash
   ip a                         # L3 config: APIPA? correct subnet?
   ip route | grep default      # gateway present?
   ping -c3 $(ip route | awk '/default/{print $3}')   # gateway reachable?
   ping -c3 1.1.1.1             # internet by IP
   dig +short example.com       # DNS
   curl -sI https://example.com # L7
   ```
   Break one layer deliberately (e.g., `sudo resolvectl dns eth0 192.0.2.1` for bogus DNS) and walk the steps to find it.
2. **Write a runbook:** create `wiki/labs/troubleshooting-runbook.md` with the 7 steps and your k3s-specific commands per step.
3. **Postmortem practice:** take your last real k3s outage and write a 1-page blameless postmortem: timeline, root cause, fix, preventive measures, lessons learned.

## Quiz

1. A technician has identified the problem and established a theory of probable cause. What is the next step?
   - A) Document findings  B) Test the theory to determine the cause  C) Implement the solution  D) Establish a plan of action

2. A technician tests a theory and it is **not** confirmed. What should they do next?
   - A) Implement the solution  B) Document findings  C) Establish a new theory or escalate  D) Verify full system functionality

3. A user says they can't print. The technician asks whether anything was installed or changed recently. Which step is this?
   - A) Identify the problem  B) Establish a theory  C) Test the theory  D) Verify functionality

4. A technician starts troubleshooting by checking the cable and link lights, then the IP configuration, then DNS, then the application. Which approach is this?
   - A) Top-to-bottom  B) Divide and conquer  C) Bottom-to-top  D) Follow the path

5. A user can reach a file server by IP address but not by hostname. What is the most likely cause?
   - A) Default gateway  B) DNS  C) Cabling  D) DHCP

6. Before applying a fix, an engineer writes down the rollback steps and checks which other services depend on the switch. Which step is this?
   - A) Test the theory  B) Establish a plan of action  C) Verify functionality  D) Document findings

7. After fixing a DHCP scope exhaustion issue, the technician confirms with users and adds a monitoring alert at 80% scope utilization. Which step does the alert belong to?
   - A) Plan of action  B) Implement the solution  C) Verify full system functionality and implement preventive measures  D) Identify the problem

8. Which is the **final** step of the troubleshooting methodology?
   - A) Verify full system functionality  B) Implement the solution  C) Document findings, actions, outcomes, and lessons learned  D) Escalate

9. A user reports two issues: their email won't sync, and a mapped drive is missing. What does the methodology recommend?
   - A) Assume one root cause  B) Escalate both immediately  C) Approach multiple problems individually  D) Reboot the workstation

10. A workstation shows the IP address 169.254.12.7. What does this indicate?
    - A) Static IP misconfiguration  B) DNS failure  C) The client failed to obtain a DHCP lease (APIPA)  D) Duplicate IP address

11. A junior tech confirms a theory that a core router needs a firmware update but lacks change authority. What is the correct action?
    - A) Apply the update after hours  B) Escalate  C) Skip to documentation  D) Establish a new theory

12. A technician begins by pinging the server, then moves up to DNS or down to the gateway depending on the result. Which approach is this?
    - A) Top-to-bottom  B) Bottom-to-top  C) Divide and conquer  D) Spot-the-difference

**Answers:** 1-B, 2-C, 3-A, 4-C, 5-B, 6-B, 7-C, 8-C, 9-C, 10-C, 11-B, 12-C
